<Chapter
  id="render-pipeline"
  n="1"
  topic="From HTML to pixels"
  question="What does the browser do between receiving HTML and showing pixels on the screen?"
  title="Five steps to a pixel."
>
  <Fragment slot="answer">
    The browser turns the HTML into a tree of elements and the CSS into a tree of rules. It combines them, computes where every box goes, draws the pixels and puts them on screen. When a script changes the page later, the browser runs only the steps that the change needs.
  </Fragment>

  <RenderPipeline />

  <Fragment slot="after">
    ### What delays the first pixels

    A stylesheet in the page's head blocks rendering by default. The browser keeps parsing the HTML while the stylesheet loads, but it does not show the first frame until it has the CSSOM. A stylesheet for another medium, such as `media="print"`, does not block the screen. The browser also does not wait for all the HTML: it can show the first frame while the rest of the page is still arriving.

    A plain `<script>` blocks parsing. The browser stops reading the HTML until it has downloaded and run the script. With `defer`, the parser continues, and the script runs after parsing, in the order of the page. With `async`, the parser also continues, but the script runs as soon as it arrives, in any order. Module scripts are deferred by default.

    ### Reading a size can force layout

    A script can change the width of a box and then read a size, such as `offsetWidth`. The layout is now out of date. To give the right answer, the browser must run style and layout at once, inside the script. This is a forced layout. A change that does not affect any size or position, such as a new background colour, makes the browser run only style before the read. A loop that changes widths and reads sizes in turn runs layout on every pass. This is called layout thrashing. To avoid it, read all the sizes first, then make all the changes.

    ### Why a page jumps

    When an element changes size after the first paint, layout may move the content around it. If visible content moves when the user does not expect it, this is a layout shift. For example, an image without a set size takes no space until it loads, then pushes the text down. Set `width` and `height` on images, so layout can keep space for them. Cumulative Layout Shift (CLS) measures unexpected layout shifts for real users.

    ### A simplified model

    Real browsers split these steps further and run some of them on other threads. Each scripted change in this demo triggers style calculation. Its cost depends on how many elements the change affects. A transform skips paint only when the element has its own layer. Browsers usually create one for a running transform animation, and `will-change: transform` asks for one in advance. Each layer uses memory, so add them only where they help.

    Test yourself with [question 1](#qz-1): it gives you a real case to apply this to.

<Chapter
  id="event-loop"
  n="2"
  topic="The event loop"
  question="What is the event loop? Why can a long task make the page feel frozen?"
  title="One thing at a time."
>
  <Fragment slot="answer">
    The main thread runs your JavaScript one task at a time. A task is one piece of work, like running a click handler. The event loop starts the next task only when the current one ends. So a tap during a long task must wait, and so does any change your code makes to the page.
  </Fragment>

  <EventLoopSim />

  <Fragment slot="after">
    ### What still moves during a long task

    Some changes do not need the main thread. The browser scrolls the page, and runs some `transform` and `opacity` animations, on a separate compositor thread. So scrolling can often continue while a long task runs. Your click handler and the changes it makes to the page cannot.

    ### Split the work, or move it

    Splitting long work into small tasks lets the event loop handle taps in between. This is called yielding. The work takes a little longer in total, but the page stays responsive. `scheduler.yield()` is made for this, but it does not work in every browser yet, so you need a fallback such as `setTimeout()`.

    A web worker takes the work off the main thread completely. A worker runs in a separate thread, but it cannot change the page directly. [Chapter 3](#web-workers) shows when that is worth it.

    ### A simplified model

    In this model a frame is due every 1/60 of a second. The screen updates only between tasks, so a frame that falls due during a task waits for that task to end. Real browsers also consider the screen's refresh rate and other work.

    The result shows the whole interaction: the wait in the queue, the handler, and the wait for the next screen update. Interaction to Next Paint (INP) measures the same span for real users. For one visit, INP reports about the slowest interaction. Across many visits, the 75th percentile is the value that counts.

    Sources, checked 23 November 2026, INP and rendering pipeline checked 25 November 2026: [web.dev, Rendering performance](https://web.dev/articles/rendering-performance), [web.dev, Optimize long tasks](https://web.dev/articles/optimize-long-tasks), [web.dev, Interaction to Next Paint](https://web.dev/articles/inp), [Long Tasks API, terminology](https://wicg.github.io/longtasks/#sec-terminology), [MDN, Scheduler.yield()](https://developer.mozilla.org/en-US/docs/Web/API/Scheduler/yield), [HTML Standard, event loop processing model](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model).
  </Fragment>
</Chapter>

<Chapter
  id="web-workers"
  n="3"
  topic="Web workers"
  question="When would you move work to a web worker?"
  title="Heavy work, another thread."
>
  <Fragment slot="answer">
    A web worker runs JavaScript on a background thread. Move work there when it is heavy and does not need the page, such as parsing a big file. The main thread stays free for typing and clicks. The result comes back in a message. Ordinary objects in a message are copied, so send back only what the page needs.
  </Fragment>

  <WorkerSim />

  <Fragment slot="after">
    ### What a worker cannot do

    A worker cannot read or change the DOM. It has no `document`. It can still use many browser features, such as `fetch()`, WebSockets and IndexedDB. So the worker does the work, and the main thread shows the result.

    The page and the worker talk with `postMessage()`. By default, the data in a message is copied, not shared. The sender writes the data into the message, and the receiver builds a new copy from it. This is called a structured clone. Most data can be copied, including a `File` or a `Blob`. Functions and DOM elements cannot: they throw a `DataCloneError`.

    A big `ArrayBuffer`, such as the bytes of a file, can be transferred instead. Transfer moves the memory to the worker without a copy. After that, the page cannot use the buffer any more: its `byteLength` is 0.

    ### Worker or small pieces

    Both keep typing fast. Small pieces are tasks on the main thread, so they can change the DOM. But you must split the work yourself, and the main thread is still busy the whole time. A worker needs no splitting and leaves the main thread free. But it cannot touch the page, and the result must travel back in a message. The row objects in this example are copied.

    For small work, a worker can make things slower: web.dev notes that the extra messages have a cost. Choose a worker for work that is heavy, can run on its own data, and returns a small result. Examples: parsing, image processing, search indexes, compression. To draw on a canvas from a worker, use `OffscreenCanvas`. It works in all core browsers.

    ### A web worker is not a service worker

    A service worker is also a worker, but it has another job. It sits between the page and the network, like a proxy. It can answer requests from a cache, for example so the site works offline.

    A service worker also runs off the main thread, but it lives differently. The browser starts it for events, such as a request, and may stop it when it has no event to handle. So it is a poor home for work that one page needs to keep, such as a parsed file the user is searching. A dedicated web worker belongs to the page that created it. The page decides when to stop it, with `terminate()`. Chapter 5 covers the HTTP cache, which works without a service worker.

    ### A simplified model

    The times in this scene are not measured. Parsing takes the same time on either thread. The 450 ms for reading all 500,000 rows on the main thread stands for a general rule: a big result costs time on the main thread when it arrives. How much depends on the data and the device. Starting a worker also costs time and memory, so the HTML Standard expects workers to be long-lived. Create one and reuse it. This model leaves the start-up out.

    The scene measures the wait before each key handler starts. The user sees the letter only after the handler ends and the browser paints the next frame, as in chapter 2.

    Test yourself with [question 3](#qz-3): it gives you a real case to apply this to.

<Chapter
  id="out-of-order"
  n="4"
  topic="Requests out of order"
  question="Two requests finish in the wrong order, and the page shows old data. Why does this happen, and how do you prevent it?"
  title="The last answer wins."
>
  <Fragment slot="answer">
    Each request takes its own time on the network, and each response arrives when it is ready. If an older request is slower, its response arrives last. Without a guard, the page shows it and replaces the newer results.
  </Fragment>

  <RaceSim />

  <Fragment slot="after">
    ### Ignore or cancel

    To ignore old responses, give each request a number. Use a response only if its number is the latest. This works for any async work, not only `fetch()`.

    To cancel the old request, pass an `AbortController` signal to `fetch()`. Call `abort()` when a new search starts. The old `fetch()` then fails with an `AbortError`, and the page should not treat that as a real error. Cancelling also means the page stops waiting for data it no longer needs.

    Sources, checked 23 November 2026: [MDN, AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController), [MDN, fetch() exceptions](https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch#exceptions).
  </Fragment>
</Chapter>

<Chapter
  id="http-caching"
  n="5"
  topic="HTTP caching"
  question="How does HTTP caching work? What do Cache-Control and ETag do?"
  title="A fresh copy never asks."
>
  <Fragment slot="answer">
    The server says how long a copy of a file stays fresh. While it is fresh, the browser uses it and asks nobody. When it turns stale, the browser checks with the server first.
  </Fragment>

  <CachingSimulator />

  <Fragment slot="after">
    ### What this model leaves out

    This is a normal visit with `Cache-Control: max-age=300` and an ETag. A reload is different. The browser checks the page itself with the server, even when its copy is fresh. Chrome may still use fresh copies of the page's other files, such as scripts, without asking. If the server sends no `Cache-Control`, the browser may choose a freshness time itself, so the old-file problem can happen by accident.

    Sources, checked 23 November 2026: [MDN, HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching), [RFC 9111, HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html#name-freshness), [RFC 9110, 304 Not Modified](https://www.rfc-editor.org/rfc/rfc9110.html#name-304-not-modified), [Chromium blog, Reload, reloaded (2017)](https://blog.chromium.org/2017/01/reload-reloaded-faster-and-leaner-page_26.html).
  </Fragment>

<Chapter
  id="memory-leaks"
  n="6"
  topic="Memory leaks"
  question="What causes memory leaks in a page that stays open for hours?"
  title="Reachable means kept."
>
  <Fragment slot="answer">
    JavaScript frees memory by itself, but only memory that nothing can reach. The garbage collector starts at a few roots, such as the page and its active timers, and follows every reference. If a timer or a listener still points to an old view, the view stays. One small leak per click adds up over hours.
  </Fragment>

  <MemorySim />

  <Fragment slot="after">
    ### What keeps memory alive

    A root is something the browser keeps as long as the page is open. The global `window` object is one. Everything it can reach stays in memory, through any chain of references. A function also keeps the variables it uses, even after the code that created it has finished. This is called a closure. So a timer's function that uses a view keeps that view alive.

    The common chains in a long-lived page:

    - An event listener on `window` or `document` that is never removed.
    - A timer from `setInterval()` that is never stopped.
    - A subscription that is never closed, for example to a WebSocket or a data store.
    - A cache or `Map` that only grows.
    - A removed element that a variable still holds.

    ### Clean up when a view closes

    Every start needs a stop. `clearInterval()` stops a timer. `removeEventListener()` removes a listener. You can also pass an `AbortSignal` in the `signal` option of `addEventListener()`. One call to `abort()` then removes every listener that uses that signal. Most frameworks give each component a cleanup step that runs when it leaves the page. Put the stops there.

    A cache needs a limit, for example the last 10 items. A `WeakMap` can also help. A DOM element can be a `WeakMap` key, and using it as a key does not keep it alive. When nothing else reaches the element, the collector can free it and its value. A string ticket ID cannot be a key, so a cache keyed by ticket ID needs a limit instead.

    ### Find the leak

    Use the Memory panel in Chrome DevTools. Take a heap snapshot to see which objects are still reachable after collection. Repeat the suspect action several times, such as opening and closing a ticket, then take a second snapshot. The Comparison view shows what was added between the two. Type `Detached` in the Class filter to find detached elements. Select one, and the Retainers section shows the chain that still points to it. The panel also has a Detached elements profile that lists them directly.

    ### A simplified model

    In this scene the collector runs after each close. Real engines decide when to collect, and code cannot start a collection. So the memory graph of a healthy page goes up and down. A leak shows as a floor that keeps rising after each collection. A detached view also keeps every element inside it, so one leaked panel can hold thousands of nodes.

    Test yourself with [question 6](#qz-6): it gives you a real case to apply this to.

    Sources, checked 25 November 2026: [MDN, Memory management](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Memory_management), [MDN, Closures](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Closures), [MDN, setInterval()](https://developer.mozilla.org/en-US/docs/Web/API/Window/setInterval), [MDN, clearInterval()](https://developer.mozilla.org/en-US/docs/Web/API/Window/clearInterval), [MDN, addEventListener()](https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/addEventListener), [MDN, WeakMap](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/WeakMap), [Chrome for Developers, Fix memory problems](https://developer.chrome.com/docs/devtools/memory-problems), [Chrome for Developers, Record heap snapshots](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots).

<Chapter
  id="runtime-validation"
  n="7"
  topic="Types and API data"
  question="Why can an app with correct TypeScript types still fail on an API response?"
  title="Types end at the build."
>
  <Fragment slot="answer">
    TypeScript checks your code before it runs, then removes the types. The API response arrives later, while the page runs, and nothing compares it with the type. If the API sends something else, the code uses it anyway. To catch it, check the data with a schema where it enters the app.
  </Fragment>

  <DataSim />

  <Fragment slot="after">
    ### A type is a promise, not a check

    TypeScript compiles your code to JavaScript, and the browser runs only the JavaScript. The compiler removes every type, every `interface` and every `as`. This is called type erasure. So a type can check how your code uses data. It cannot check the data itself.

    In the browser's type definitions, `res.json()` returns `Promise<any>`. So the value you get after `await` has the type `any`. `any` turns off type checking, so you can use the value as anything. `as Order` is a type assertion: it tells the compiler "trust me, this is an Order". The TypeScript handbook says there is no runtime check for a type assertion. A typed wrapper around `fetch()` that ends in `as T` does the same thing in another place.

    Bad data does not always crash. In the scene, `"42.95" + 5` joins two strings and gives `"42.955"`. A missing field gives `undefined`, which the page can show as text. A crash at least shows up in your error reports. A wrong value on the screen often does not.

    ### Check where data enters the app

    A schema describes the shape of the data in ordinary code. A schema library checks a value against it while the page runs. It returns the data, typed, or an error that names each field that failed. Check once, at the edge of the app. The code after that can trust the type, because something checked it.

    The edges are every place where data comes from outside your code: API responses, `localStorage`, URL parameters, messages from a worker or a WebSocket, and JSON files. Inside the app, the types are enough.

    Write the schema once and get the type from it, so the two cannot drift apart. In Zod, `z.infer<typeof Order>` gives the type. In Valibot, `v.InferOutput<typeof Order>` does. A schema also removes fields you did not list: by default a Zod object drops unknown keys from the result.

    ### Throw, or handle the result

    `Order.parse(data)` returns the data or throws an error. `Order.safeParse(data)` does not throw when the data is invalid. It returns an object with `success: true` and the data, or `success: false` and the error. One exception: a schema with an async check, such as a refinement that calls a server, needs `parseAsync()` or `safeParseAsync()`. Plain `safeParse()` throws on it. Valibot has the same pair: `v.parse()` throws a `ValiError`, and `v.safeParse()` returns a result.

    Either way, decide what the page does with bad data. Show a message and a way to retry. Or show the parts you can trust, with a default for the rest. Always send the error to your error reports. The error names the field, so you can see which API change broke the page.

    Zod and Valibot do the same job in different styles. [Current tools](#tools) compares them.

    ### What a schema cannot do

    A schema checks the shape of the data, not whether it is true. A total of `42.95` passes even if the right total is `52.95`. A schema can also be out of date, like a type. It catches only changes that break one of its rules. In the scene, the new status "returned" breaks the `z.enum()` rule, so `parse()` fails. But if the API adds a new field, such as `tax`, the check passes: a Zod object drops fields it does not list and returns success. Your code never sees `tax`, and nobody is told. To be told about new fields, use `z.strictObject()`, which fails on unknown fields. Then the page breaks on every harmless addition, so most apps accept the default.

    Each check costs some time while the page runs. For a normal API response this is small. For a large response, measure it, or check it in a [web worker](#web-workers). Types generated from an OpenAPI file are still only types: they keep the code and the API description in step, but they do not check the response. And checking on the client never protects the server. The server must check everything it receives.

    ### A simplified model

    The scene uses Zod's real error messages. Valibot's message for the same total reads `Invalid type: Expected number but received "42.95"`. In a real app, the error would go to an error boundary or a handler that shows the message and reports the error.

    Test yourself with [question 7](#qz-7): it gives you a real case to apply this to.

<Chapter
  id="browser-support"
  n="8"
  topic="Browser support"
  question="How do you decide which browsers to support, and what happens in older ones?"
  title="Works everywhere, better where it can."
>
  <Fragment slot="answer">
    Start with your users, not with a list of features. Write the target down once, so every tool uses the same one. Use a feature directly only if every browser in the target has it. For the rest, make sure the core task still works without it.
  </Fragment>

  <BrowserSupport />

  <OlderBrowser />

  <Fragment slot="after">
    ### Decide with your own users

    Baseline describes browsers, not your users. In December 2024, a web.dev case study measured real visitors on three sites. Features from Baseline 2024 worked for 34%, 59% and 39% of them. Widely available features worked for 95% to 100%. So check your own analytics before you choose a target, especially for key tasks such as checkout. Supporting a browser means that its core tasks work. It does not mean that the page looks the same everywhere.

    ### Write the target once

    browserslist keeps the target in one place, in `package.json` or a `.browserslistrc` file. Autoprefixer and Babel read it by default, and Lightning CSS can be pointed at it, so they all prepare the code for the same browsers. Since version 4.26, it accepts Baseline queries such as `baseline widely available` or `baseline 2022`. Its `defaults` query works differently: it picks browsers by usage share from Can I Use data, `> 0.5%, last 2 versions, Firefox ESR, not dead`.

    ### What an older browser does

    A browser skips what it does not understand. In CSS, it drops a declaration with an unknown property or value. It drops a whole rule if the selector is unknown, which is what happens to the `:has()` rule in the scene. Firefox 120, from November 2023, is old enough to lack `:has()` and popover, and still inside a Baseline 2022 target. So the effect of a missing feature depends on its job:

    - **An extra**, such as a highlight or `text-wrap: balance`. The page loses some polish and still works. No fallback code is needed.
    - **A layout**, such as `@container`. Write a simple layout first, then add the new one on top, or put it inside `@supports`. The older browser keeps the simple layout.
    - **A behaviour**, such as `popover`. Without it, a control does nothing. It needs a small script, or a polyfill that loads only when the feature is missing.
    - **The foundation**, such as `@layer`. Layers decide which rules win. A browser without them skips every layer block and all the rules inside it. If some browsers in your target lack layers, the styles the page needs must not live inside them.

    Chrome's Modern Web Guidance uses the same four kinds of fallback: none, `@supports`, a small script, or a polyfill loaded only when needed.

    ### Check the feature, not the browser

    In CSS, `@supports` tests one property or selector, for example `@supports selector(:has(a))` or `@supports (anchor-name: --tip)`. In JavaScript, test the API itself. MDN checks for popover with `Object.hasOwn(HTMLElement.prototype, 'popover')`. A check answers only the question you ask. `anchor-name` passes in Firefox 147, but one part of anchor positioning is still missing there. Test the part your page uses.

    ### Semantic HTML is the base layer

    Native elements bring their behaviour with them. A `<button>` works with a keyboard and a screen reader in every browser. A `<form>` with a `<label>` for each field and a submit button sends its data even when your JavaScript fails. Build the core task with these elements, then add newer features on top. This is progressive enhancement.

    Logical properties belong in the base layer too. `margin-inline-start` means the side where a line starts, not the left side. In a right-to-left language such as Arabic, `dir="rtl"` moves it to the right with no extra CSS. Logical properties have been Widely available since March 2024.

    ### A simplified model

    The dates come from the web-features data behind Baseline, version 3.48.0. A Baseline year target includes every browser version that supports all the features that were Newly available at the end of that year. For 2022, that goes back to Safari 16 and Firefox 108. The chart is fixed at 27 November 2026; in reality the Widely available line moves forward every day. Baseline rates whole features. The basic `popover` attribute became Widely available on 16 October 2026, but the feature as a whole is Newly available until iOS Safari 18.3 is 30 months old. Anchor positioning counts as Limited because Firefox lacks two values of `position-visibility`. Its main properties, such as `anchor-name`, have worked in all core browsers since January 2026. The scene is drawn, not live: a page cannot switch features off in your browser.

    Test yourself with [question 8](#qz-8): it gives you a real case to apply this to.

  ### Summary

  <ol class="rv-summary">
    <li><span>The browser builds the DOM and the CSSOM, lays out the boxes, paints and composites. A later change runs only the steps it needs. [HTML to pixels](#render-pipeline)</span></li>
    <li><span>The main thread runs one task at a time, so a tap waits behind a long task. Split the work, or move it. [Event loop](#event-loop)</span></li>
    <li><span>Move heavy work that does not need the DOM to a worker, and send back only a small result. [Web workers](#web-workers)</span></li>
    <li><span>Responses arrive in any order. Apply a response only if it belongs to the latest request; cancel old requests to save work. [Out of order](#out-of-order)</span></li>
    <li><span>A fresh copy is used without asking the server. A stale copy is checked with the server first, usually with its ETag. [HTTP caching](#http-caching)</span></li>
    <li><span>Memory stays while anything can reach it. Stop every timer, listener and subscription you start. [Memory leaks](#memory-leaks)</span></li>
    <li><span>Types are removed at build time. Check outside data with a schema where it enters the app. [API data](#runtime-validation)</span></li>
    <li><span>Choose a browser target from your users' data. The core task works everywhere; newer features add to it. [Browsers](#browser-support)</span></li>
  </ol>

  ### Key terms

  <div class="rv-terms">
    <div>
      <h4>[1 · HTML to pixels](#render-pipeline)</h4>
      <dl>
        <dt>DOM and CSSOM</dt><dd>The trees the browser builds from the HTML and from the CSS.</dd>
        <dt>Layout</dt><dd>Computing the size and position of every box.</dd>
        <dt>Paint and composite</dt><dd>Drawing pixels into layers, then putting the layers on screen.</dd>
        <dt>Forced layout</dt><dd>A script reads a size after a change, so layout runs at once, inside the script.</dd>
        <dt>Layout shift and CLS</dt><dd>Visible content moves when the user does not expect it. CLS scores the worst burst of such shifts in a visit.</dd>
      </dl>
    </div>
    <div>
      <h4>[2 · Event loop](#event-loop)</h4>
      <dl>
        <dt>Main thread</dt><dd>The one thread that runs your page's JavaScript and updates the page.</dd>
        <dt>Task and long task</dt><dd>One piece of work. A long task runs for more than 50 ms.</dd>
        <dt>Yielding</dt><dd>Ending a task early, so the browser can handle input in between.</dd>
        <dt>INP</dt><dd>Interaction to Next Paint: about the slowest interaction in a visit, from input to the next screen update. 200 ms or less is good.</dd>
      </dl>
    </div>
    <div>
      <h4>[3 · Web workers](#web-workers)</h4>
      <dl>
        <dt>Web worker</dt><dd>JavaScript on a background thread. It cannot touch the DOM.</dd>
        <dt>Structured clone</dt><dd>How a message is copied between the page and a worker.</dd>
        <dt>Transfer</dt><dd>Moving an <code>ArrayBuffer</code> to the worker without a copy.</dd>
        <dt>Service worker</dt><dd>A worker that sits between the page and the network, like a proxy.</dd>
      </dl>
    </div>
    <div>
      <h4>[4 · Out of order](#out-of-order)</h4>
      <dl>
        <dt>Race condition</dt><dd>The result depends on the order in which responses arrive.</dd>
        <dt>Request number</dt><dd>A counter that tells the page which response is the latest.</dd>
        <dt>AbortController</dt><dd>Cancels a <code>fetch()</code>. The cancelled call fails with an <code>AbortError</code>.</dd>
      </dl>
    </div>
    <div>
      <h4>[5 · HTTP caching](#http-caching)</h4>
      <dl>
        <dt>Fresh and stale</dt><dd>A fresh copy is used without asking. A stale copy is checked first.</dd>
        <dt><code>max-age</code></dt><dd>How many seconds a copy stays fresh.</dd>
        <dt>ETag and 304</dt><dd>A version label for a file. 304 means "not changed, keep your copy".</dd>
        <dt><code>no-cache</code> and <code>no-store</code></dt><dd>Check before each use, or do not store at all.</dd>
      </dl>
    </div>
    <div>
      <h4>[6 · Memory leaks](#memory-leaks)</h4>
      <dl>
        <dt>Garbage collector</dt><dd>Frees memory that nothing can reach.</dd>
        <dt>Root</dt><dd>Something the page always keeps, such as <code>window</code> or an active timer.</dd>
        <dt>Closure</dt><dd>A function keeps the variables it uses alive.</dd>
        <dt>Detached element</dt><dd>Removed from the page, but still held by code.</dd>
        <dt>Heap snapshot</dt><dd>A list of everything in memory, to compare before and after an action.</dd>
      </dl>
    </div>
    <div>
      <h4>[7 · API data](#runtime-validation)</h4>
      <dl>
        <dt>Type erasure</dt><dd>The compiler removes all types, so none exist while the page runs.</dd>
        <dt>Type assertion</dt><dd><code>as Order</code>: tells the compiler to trust you. Nothing is checked.</dd>
        <dt>Schema</dt><dd>A description of the data that runs as code and checks values.</dd>
        <dt>Edge of the app</dt><dd>Any place where outside data enters: APIs, storage, URLs, messages, model output.</dd>
      </dl>
    </div>
    <div>
      <h4>[8 · Browsers](#browser-support)</h4>
      <dl>
        <dt>Core browsers</dt><dd>Chrome, Edge, Firefox and Safari, on desktop and mobile.</dd>
        <dt>Newly and Widely available</dt><dd>In every core browser; and 30 months after that.</dd>
        <dt>Limited availability</dt><dd>Missing from at least one core browser.</dd>
        <dt>Progressive enhancement</dt><dd>The core works everywhere. Newer features add to it.</dd>
        <dt>Feature detection</dt><dd>Testing for the feature itself, with <code>@supports</code> or a check in JavaScript.</dd>
      </dl>
    </div>

  ### Trade-offs

  <div class="rv-table" style="--c2: 'Choose the first when'; --c3: 'Choose the second when'">

  | Choice | Choose the first when | Choose the second when |
  |---|---|---|
  | `defer` or `async` | The script needs the parsed page, or another script, in order. | The script stands alone, such as analytics. |
  | Small pieces or a [worker](#web-workers) | The work must change the DOM. | The work is heavy, has its own data and returns a small result. |
  | Ignore or [cancel](#out-of-order) old responses | The work is not a `fetch()`, or you cannot cancel it. | You also want to stop downloading data nobody needs. Still check that the response is the latest. |
  | Long `max-age` or [`no-cache`](#http-caching) | The file name changes with each version, such as `app.3f9a.js`. | The name stays the same, such as the HTML page. |
  | A size limit or a [`WeakMap`](#memory-leaks) | The keys are strings or numbers, such as ticket IDs. | The keys are objects, such as DOM elements. |
  | A type only or a [schema](#runtime-validation) | The data comes from your own code. | The data comes from outside the app. |
  | Default object or `z.strictObject()` | A new field from the API should not break the page. | You must know about every new field. |
  | Use directly or a [fallback](#browser-support) | Every browser in your target has the feature. | Some do, and the core task depends on it. |

  </div>

  ### What AI has changed

  - **Agents often get browser support wrong.** Chrome's Modern Web Guidance team says coding agents rarely check the project's browser target. They rebuild built-in features in JavaScript, or use new features without a fallback. On Chrome's own tests for features that are not in every core browser, unguided models added a feature check or fallback 43% of the time, and 87% with the guidance. These are Google's numbers for Google's tool. Write your target in AGENTS.md or CLAUDE.md, and check fallbacks in review.
  - **Agents can now see the running page.** With Chrome DevTools for agents, an agent can record a performance trace or take heap snapshots to find detached elements. It can collect the evidence from chapters 1, 2 and 6. A person still has to judge it.
  - **Model output is outside data.** JSON Schema is how many AI APIs describe structured output, and Zod 4 can produce it. A response in the right shape can still hold wrong values, so the rule from chapter 7 applies: check it where it enters the app.
  - **AI in the browser is not Baseline yet.** The Translator, Language Detector and Summarizer APIs work only in desktop Chrome 138 and later and in Edge. Treat them like any Limited feature: an extra with a fallback.

  No primary source shows whether AI has changed how often teams use workers or caching, so this guide makes no claim about it.

The user sees a frozen page, even if scrolling still works, because the browser scrolls on a separate compositor thread.     A worker is not free. It cannot change the page. Data in a message is copied by default, which is called structured cloning.       'max-age says how many seconds a copy stays fresh.',
      'A fresh copy is used without contacting the server.',
      'A stale copy is checked: the browser sends If-None-Match with the ETag.',
      '304 means no body, keep the copy. 200 means here is a new file.',
      'Common policy: hashed file names with a long max-age, and no-cache for HTML.',
    ]}
  >
    `Cache-Control` tells the browser how long a copy stays fresh, for example `max-age=3600` for one hour. While it is fresh, the browser uses it and sends no request. After that, the copy is stale. The browser asks the server whether it changed and sends the `ETag`, a version label for the file, in `If-None-Match`. The server answers `304 Not Modified` with no body, or `200` with the new file.

    A common policy: give static files a new name for each version, such as `app.3f9a.js`, and cache them for a long time. Send HTML with `no-cache`, which means the browser may store it but must check before each use. `no-store` means do not store it at all.
  </QuizItem>

  <QuizItem
    n="6"
    art="memory"
    href="#memory-leaks"
    question="What causes memory leaks in a page that stays open for hours?"
    scenario="A dashboard stays open all day. Each time the user opens a panel, the code adds a resize listener on window. The listener's function uses the panel, to resize it. Closing the panel removes it from the page, but not the listener. What happens over the day?"
    options={[
      'Nothing. The garbage collector frees each panel when it leaves the page.',
      'The browser removes the listener when the panel leaves the page.',
      'Memory grows with every open. Each listener’s function still refers to its own panel.',
      'Memory grows while a panel is open, then drops back when it closes.',
    ]}
    correct={2}
    why="The garbage collector frees only memory that nothing can reach. window lives as long as the page and keeps every listener. Each listener's function still refers to its own panel. So every closed panel stays in memory."
    evidence={{
      question: 'Which evidence would confirm the leak?',
      answer: 'Heap snapshots in the DevTools Memory panel, taken before and after opening and closing the panel several times. The number of detached elements grows with each round, and their retainers lead to the resize listener.',
    }}
    myth="Removing an element from the page does not free it. If any code still refers to it, it stays in memory as a detached element."
    points={[
      'Garbage collection frees only what nothing can reach.',
      'Listeners, timers and subscriptions that are never removed.',
      'Caches and maps that only grow.',
      'Detached DOM elements still held by code.',
      'Find them with heap snapshots in the DevTools Memory panel.',
    ]}
  >
    JavaScript frees memory by itself, but only memory that nothing can reach any more. A leak happens when something long-lived keeps a reference to something you no longer need. Common examples: an event listener or timer that is never removed, a subscription that is never closed, a cache that only grows, or a removed element that a variable still holds.

    Each one is small, but the page repeats it for hours. To find them, take heap snapshots in the DevTools Memory panel before and after a repeated action, and compare. Look for detached elements. To fix them, remove listeners, timers and subscriptions when a component closes.
  </QuizItem>

    TypeScript checks your code before it runs. The API response arrives later, while the page runs. By then the types are gone: TypeScript removes them when it compiles to JavaScript. So a type is a promise you make, not a check.

    To make it safe, check the data where it enters the app. A schema library such as Zod or Valibot checks the response and gives you typed data, or a clear error. Then decide what the page does with bad data: show a message, use a default, or report it.
