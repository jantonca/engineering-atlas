<Chapter
  id="choose-task"
  n="1"
  topic="Choose the task"
  question="When should you not use an AI agent for a task?"
  title="Hand over what you can check."
>
  <Fragment slot="answer">
    Ask two questions. How easy is the result to check? And what does a mistake cost? Hand over work you can check faster than you could write it, where a mistake is easy to undo. When checking is hard and a mistake is costly, do the work yourself and use AI for parts of it. Good tests change the answer, because they make more work easy to check.
  </Fragment>

  <TaskPlot />

  <Fragment slot="after">
    ### What engineers say they hand over

    Anthropic asked its own engineers how they use Claude. They "tend to delegate tasks that are easily verifiable", low-stakes, such as "throwaway debug or research code", or boring. They also hand over parts that are well defined and separate from the rest. More than half said they can "fully delegate" only 0 to 20% of their work. This is one company's self-report, so treat it as a description, not a rule. It matches the two axes of the plot.

    ### Checking is part of the cost

    The time you spend reviewing counts. If reading a 600-line diff takes longer than writing the change would, the agent saved nothing. People are poor judges of this, as [chapter 6](#measure) shows. So pick tasks where the check is fast: a type error, a failing test, a screen you can look at.

    ### Agents that work in the background

    Cloud agents take a task, work on their own branch and return a pull request. GitHub Copilot's cloud agent, Codex Cloud and Cursor's Cloud Agents all work this way. They suit tasks on the right of the plot: well defined, and easy to check from the diff and the CI results.

    ### A simplified model

    The positions are a judgement for a typical team, not a measurement. Two things move a task. Better checks, such as tests, types or a preview build, move it to the right. A cheap way to undo a mistake lowers it. Guide 12 covers feature flags and rollback, which lower the cost of a mistake.

    Sources, checked 27 November 2026: [Anthropic, How AI is transforming work at Anthropic (2025)](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic), [GitHub Docs, About Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent), [Codex Cloud environments](https://learn.chatgpt.com/codex/environments/cloud-environments), [Cursor, Cloud Agents](https://cursor.com/docs/cloud-agent).
  </Fragment>
</Chapter>

<Chapter
  id="context"
  n="2"
  topic="Give it context"
  question="What context does an agent need, and where should it live?"
  title="Every line costs, every task."
>
  <Fragment slot="answer">
    An agent reads its instruction file, such as `AGENTS.md`, at the start of every task. Keep that file for rules the agent cannot find in the code and would get wrong. Put long procedures in skills, which load only when a task needs them. If a rule must never break, enforce it with a hook or a permission rule; a sentence is only a request. Leave out what the agent can find by itself, such as the folder layout.
  </Fragment>

  <ContextSort />

  <Fragment slot="after">
    ### What a 2026 study found

    Researchers tested coding agents on real repository tasks, with and without context files such as `AGENTS.md`. The files "did not generally improve task success rates". They raised the cost by more than 20% on average, because the agent reads and follows more text. The agents followed the instructions well. But "repository overviews … are not helpful". The files were useful "for specifying non-standard coding practices". The tasks came from public repositories, so test what works in yours.

    ### Where instruction files live

    `AGENTS.md` is an open format: plain Markdown, with no required fields. "The closest AGENTS.md to the edited file wins." Codex, GitHub Copilot, Cursor, Kiro and CodeRabbit read it. Codex joins the files from the repository root down to the current folder, up to 32 KiB by default. Claude Code reads `CLAUDE.md`, and by default reads `AGENTS.md` only when there is no `CLAUDE.md`. To use one file for both, put `@AGENTS.md` in `CLAUDE.md`, as this site does. Gemini CLI reads `GEMINI.md`, and can be set to read `AGENTS.md`.

    Claude Code's documentation is direct about the limit: instruction files "aren't enforced configuration". To block an action, use a hook. A `PreToolUse` hook runs before a tool call and can stop it. Use a deny rule in the permission settings for a hard block.

    ### Skills load in steps

    A skill is a folder with a `SKILL.md` file. Its `name` and `description` load when the agent starts, about 100 tokens per skill. The rest of the file loads only when a task needs it. Any scripts or reference files in the folder load only when they are used. Anthropic published Agent Skills as an open standard in December 2025. In October 2026 it gave the standard to the Agentic AI Foundation, and said more than 70 agent products support it.

    ### Subagents keep side work out of the way

    A subagent runs a side task, such as searching 200 files, in its own context window. Only its summary comes back to the main task. The summary still takes space there, so ask for a short one.

    ### MCP servers add tools and data

    The Model Context Protocol (MCP) connects an agent to outside tools and data, such as GitHub, a database or a browser. Each server is code you choose to trust. The specification says tool descriptions "should be considered untrusted, unless obtained from a trusted server". [Chapter 3](#limits) shows what can go wrong.

    ### The brief matters most

    For one task, give the goal, the files that matter, the limits, and one example of the right result. That example is also how you check the work in [chapter 4](#check). How a model uses the text in its context window is the topic of guide 15.

    Sources, checked 27 November 2026: [Gloaguen et al., Evaluating AGENTS.md (arXiv, 2026)](https://arxiv.org/abs/2602.11988), [AGENTS.md](https://agents.md/), [Codex, AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [Claude Code, Memory](https://code.claude.com/docs/en/memory), [Claude Code, Hooks](https://code.claude.com/docs/en/hooks), [Claude Code, Subagents](https://code.claude.com/docs/en/sub-agents), [Agent Skills specification](https://agentskills.io/specification), [Anthropic, Donating Agent Skills to the Agentic AI Foundation (2026)](https://www.anthropic.com/news/donating-agent-skills-to-the-agentic-ai-foundation), [GitHub Docs, Custom instructions support](https://docs.github.com/en/copilot/reference/custom-instructions-support), [Cursor, Rules](https://cursor.com/docs/context/rules), [Gemini CLI, GEMINI.md](https://geminicli.com/docs/cli/gemini-md/), [MCP specification](https://modelcontextprotocol.io/specification).
  </Fragment>

<Chapter
  id="limits"
  n="3"
  topic="Set limits"
  question="How would you introduce AI coding tools to a team safely?"
  title="Give each task only what it needs."
>
  <Fragment slot="answer">
    The danger is a combination. An agent that reads text from outside, can reach private data and can send data out can be tricked into leaking that data. For each task, remove one of the three, usually by giving the agent a narrower token. Then start small: one repository, written rules about what data may leave it, and a person who reviews every change.
  </Fragment>

  <ScopeSim />

  <Fragment slot="after">
    ### The lethal trifecta

    Simon Willison named the three conditions in June 2025: "access to your private data", "exposure to untrusted content", and "the ability to externally communicate". If an agent has all three, "an attacker can easily trick it into accessing your private data and sending it to that attacker". He also wrote that "we still don't know how to 100% reliably prevent this". So do not count on the model to refuse. Change what it can reach.

    ### What happened in May 2025

    Invariant Labs showed the attack in the scene, using demo repositories. An attacker opens an issue in a public repository with hidden instructions. The user asks the agent, Claude Desktop with the GitHub MCP server, to look at the open issues. The agent reads a private repository and puts its contents in a public pull request. The app asked before each tool call, but the researchers note that many users choose "Always Allow". They also say it is "not a flaw in the GitHub MCP server code itself". The problem is what the token could reach.

    ### Prompts, modes and sandboxes

    A prompt before every action sounds safe. But after the fiftieth prompt, people approve without reading. So agents offer modes. Claude Code has modes from Manual, which asks before most actions, to `bypassPermissions`, which is meant for isolated containers only. Its deny rules apply in every mode. Codex runs in a sandbox: `read-only`, `workspace-write` or `danger-full-access`. The interactive CLI starts in `workspace-write`, with network access off; `codex exec`, used in scripts and CI, starts in `read-only`.

    Some tools now let a model decide which actions need a person. Claude Code's auto mode uses a separate classifier. It is now the starting mode in the terminal and in VS Code; `claude -p` and the Agent SDK still start in Manual. GitHub Copilot's assisted permissions became generally available in October 2026. Claude Code's documentation says auto mode "does not guarantee safety".

    A sandbox limits what a command can touch. In Claude Code it "covers shell commands only": file edits, hooks and local MCP servers run outside it. So a sandbox would not have stopped the attack above. The MCP server called GitHub with the token, and the token allowed it.

    ### Cloud agents come with limits

    GitHub Copilot's cloud agent can be started only by people with write access. It pushes to its own branch, or to the pull request it was asked to work on. A firewall limits the internet access of its shell commands, but not of other MCP servers or of setup steps. By default, CI workflows wait until a person approves them. It "cannot approve or merge a pull request", and the person who asked for the change cannot approve it either. Several of these are defaults that repository settings can change: for example, Copilot code review can be allowed to count as an approval. Check yours, and decide whether a person must approve every agent change.

    ### Any program can use an agent

    In August 2025, attackers published malicious versions of the Nx build tool to npm. For about 4 hours, installing them ran code that "attempted to use local AI tools (like Claude and Gemini)" to search the disk for secrets. The stolen secrets went to public GitHub repositories. An agent that runs with no limits is a tool that any code on the machine can use. Guide 9 covers the npm supply chain.

    ### A small pilot

    1. Choose one repository and low-risk tasks from the right side of [chapter 1](#choose-task).
    2. Write down which data may go to which tool provider.
    3. Commit the shared instruction file and permission settings, so everyone starts with the same limits.
    4. Give every agent change a human reviewer. Agents do not merge.
    5. Decide in advance what would make you widen the pilot or stop it, such as review time, rework or incidents. [Chapter 6](#measure) covers how to measure them.

    Prompt injection in a product you build is the topic of guide 16.

    Sources, checked 27 November 2026: [Simon Willison, The lethal trifecta (2025)](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/), [Invariant Labs, GitHub MCP exploited (2025)](https://invariantlabs.ai/blog/mcp-github-vulnerability), [Claude Code, Permission modes](https://code.claude.com/docs/en/permission-modes), [Claude Code, Sandboxing](https://code.claude.com/docs/en/sandboxing), [Codex, Sandboxing](https://learn.chatgpt.com/docs/sandboxing), [Codex, Approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security), [GitHub Changelog, Assisted permissions (2026)](https://github.blog/changelog/2026-10-26-github-copilot-assisted-permissions-generally-available/), [GitHub Docs, Copilot cloud agent risks and mitigations](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations), [Nx, s1ngularity postmortem (2025)](https://nx.dev/blog/s1ngularity-postmortem), [GitHub advisory GHSA-cxm3-wv7p-598c](https://github.com/advisories/GHSA-cxm3-wv7p-598c).
  </Fragment>

<Chapter
  id="check"
  n="4"
  topic="Check the result"
  question="How do you check what an agent produces?"
  title="Read it against the requirement."
>
  <Fragment slot="answer">
    Compare the diff with the requirement, not with the agent's summary. Run the change. Look hardest at the tests. An agent that cannot make a test pass may change the test instead, and then every check is green. AI review is a useful second reader. But it reads the same diff, and it can accept the same wrong idea of the task.
  </Fragment>

  <DiffCheck />

  <Fragment slot="after">
    ### What to look for in an agent's diff

    - Tests that were changed or deleted in the same change as the code.
    - Checks that were skipped, loosened or wrapped in a retry.
    - New dependencies. Check that each one exists and is the package you meant.
    - Changes outside the task: files the request never mentioned.

    ### Agents can aim at the check

    METR saw recent models "attempting (often successfully) to get a higher score by modifying the tests or scoring code" in its evaluations, June 2025. The examples were evaluation tasks, not team repositories. But the pressure is the same in your repository: the agent is asked to make the checks pass.

    ### Check every new package

    A 2025 study asked 16 models to write code and checked the packages they used. At least 5.2% of packages suggested by commercial models, and 21.7% by open models, did not exist. It found 205,474 different made-up names. An attacker can publish a package under such a name. Guide 9 covers the supply chain.

    ### AI review is a second reader

    GitHub Copilot code review, Codex review and CodeRabbit comment on pull requests. By default, Copilot's reviews "do not count toward required approvals". Codex flags only the most serious issues, P0 and P1, and follows review rules written in `AGENTS.md`. CodeRabbit also reads `AGENTS.md` and `CLAUDE.md` as review rules. Use them to find more problems before a person reads the change, not to decide that it is right.

    ### Write the acceptance criterion first

    Spec-first tools ask for the requirement before any code is written. GitHub Spec Kit steps through a project constitution, then specify, plan, tasks and implement. Kiro writes `requirements.md`, `design.md` and `tasks.md` for each feature. We found no independent study that shows these tools give better results. For most tasks, a few lines of criteria with one or two examples, reviewed by a person, do the same job. Guide 7 covers which tests to write at which level.

    ### How much developers trust it

    In Stack Overflow's 2026 survey, 48% said they trust AI output "when they can easily validate the answers". In the DORA 2025 survey, 30% trusted AI-generated code little or not at all.

    Sources, checked 27 November 2026: [METR, Recent frontier models are reward hacking (2025)](https://metr.org/blog/2025-06-05-recent-reward-hacking/), [Spracklen et al., Package hallucinations (USENIX Security 2025)](https://arxiv.org/abs/2406.10279), [GitHub Docs, Copilot code review](https://docs.github.com/en/copilot/concepts/agents/code-review), [Codex, GitHub integration](https://learn.chatgpt.com/docs/third-party/github), [CodeRabbit, Code guidelines](https://docs.coderabbit.ai/knowledge-base/code-guidelines), [GitHub Spec Kit](https://github.com/github/spec-kit), [Kiro, Specs](https://kiro.dev/docs/specs/), [Stack Overflow Developer Survey 2026, AI](https://survey.stackoverflow.co/2026/ai), [Google Cloud, DORA 2025 report](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report).
  </Fragment>
</Chapter>

<Chapter
  id="learning"
  n="5"
  topic="Keep learning"
  question="Does AI change how junior engineers should learn?"
  title="Ask why, then write it yourself."
>
  <Fragment slot="answer">
    It changes how they should use it. In a 2026 trial, people learning a new library with an AI assistant scored 4.15 points lower on a 27-point quiz straight afterwards. The biggest gap was in debugging, and they were not clearly faster. In the AI group, people who asked about concepts, or asked why the code worked, tended to score higher than those who handed the task over. So use AI to explain. Write the code, debug it and explain it yourself.
  </Fragment>

  <SkillStudy />

  <Fragment slot="after">
    ### When you are learning something new

    - Try it first, then ask. A wrong first attempt teaches more than a right answer you only read.
    - Ask why, not only how. "Why does this need a lock?" teaches more than "write the lock".
    - Debug alone for a while before you ask. Debugging showed the biggest gap.
    - Before you merge, explain the change to someone, line by line.

    ### When you review or mentor

    Ask the author to explain the change in their own words. Pair on the parts that are hard to check. Some tasks are worth doing by hand because the point is to learn, even when an agent could do them faster.

    ### Limits of the study

    The trial had 52 people, and the quiz came straight after the task, so it does not show long-term effects. The AI was a chat assistant, not an agent that edits files and runs commands. The authors expect the effect of agents on learning to be "more pronounced". Anthropic's blog post gives the scores as 50% and 67%, which does not match the paper's 4.15-point gap on a 27-point quiz. This guide uses the paper.

    ### Developers worry too

    In Stack Overflow's 2026 survey, the most common reason to avoid AI at work was "Concern over losing job skills or training an AI to replace you": 17.1% of 13,857 people. The answer joins two worries, so it does not measure fear of losing skills alone.

    Sources, checked 27 November 2026: [Shen and Tamkin, How AI impacts skill formation (arXiv, 2026)](https://arxiv.org/html/2601.20245v3), [Anthropic, How AI assistance impacts the formation of coding skills (2026)](https://www.anthropic.com/research/AI-assistance-coding-skills), [Stack Overflow Developer Survey 2026, reasons to avoid AI](https://survey.stackoverflow.co/2026/ai/data/ai-avoid).
  </Fragment>
</Chapter>

<Chapter
  id="measure"
  n="6"
  topic="Measure"
  question="How would you measure whether AI tools actually help?"
  title="Felt faster is not faster."
>
  <Fragment slot="answer">
    Do not ask people how much faster they feel. In a 2025 trial, experienced developers expected AI to make them 24% faster. Afterwards they felt 20% faster, but they took 19% longer. Measure the work instead: compare similar tasks for time to merge, review time, rework and defects after release. Count stability as well as speed.
  </Fragment>

  <TaskTime />

  <Fragment slot="after">
    ### Why the follow-up could not give a number

    METR ran the trial again from August 2025, with 57 developers and more than 800 tasks. It calls the result "an unreliable signal". Developers who did not want to work without AI stayed away. Of those who joined, 30 to 50% said they held back tasks they did not want to do without AI. METR thinks both effects likely hide part of the gain. It thinks developers are probably faster now, but has "only very weak evidence for the size". The lesson for a team is the same: who takes part, and which tasks they pick, can change the result.

    ### Self-reports run high

    METR also surveyed 349 technical workers in early 2026. The median said AI made their work 1.4 to 2 times as valuable. METR warns that "survey results are not necessarily grounded in reality". Surveys are still useful to learn what people like and what blocks them. They are not a measure of speed.

    ### What to measure on your team

    Compare similar work, before and after, or between two groups at the same time:

    - time from the first commit to merge
    - time spent in review
    - rework: changes that are reverted, or fixed again soon after
    - defects and incidents after release
    - cost: seats and usage

    Guide 12 explains delivery metrics such as DORA's in detail.

    ### AI amplifies what is there

    DORA's 2025 survey had nearly 5,000 respondents. 90% used AI at work, and more than 80% said it raised their productivity. More AI use went with more throughput, and with less stable delivery. "AI doesn't fix a team; it amplifies what's already there." These are associations in a survey, not causes. DORA lists seven capabilities that help: a clear AI stance, healthy data, AI access to internal data, strong version control, small batches, a focus on users, and good internal platforms. As of 27 November 2026, dora.dev lists no 2026 annual report.

    Sources, checked 27 November 2026: [METR, Early-2025 AI and experienced developers (2025)](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/), [METR, Changing our developer productivity experiment design (2026)](https://metr.org/blog/2026-02-24-uplift-update/), [METR, Self-reported impact of early-2026 AI (2026)](https://metr.org/blog/2026-05-11-ai-usage-survey/), [Google Cloud, Announcing the 2025 DORA report](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report), [DORA, 2025 report](https://dora.dev/dora-report-2025/), [Google Cloud, DORA AI Capabilities Model](https://cloud.google.com/blog/products/ai-machine-learning/introducing-doras-inaugural-ai-capabilities-model), [DORA research archive](https://dora.dev/research/).

  ### Trade-offs

  <div class="rv-table" style="--c2: 'Choose the first when'; --c3: 'Choose the second when'">

  | Choice | Choose the first when | Choose the second when |
  |---|---|---|
  | An agent or [yourself](#choose-task) | You can check the result faster than you could write it, and a mistake is easy to undo. | Checking is hard and a mistake is costly, or the point is to learn. |
  | A local or a cloud agent | You want to steer while it works. | The task is well defined, and you will review a pull request. |
  | `AGENTS.md` or a [skill](#context) | Almost every task needs the rule. | It is a long procedure that a few tasks need. |
  | A sentence or a [hook or rule](#context) | Breaking it is cheap and easy to spot. | It must never happen. |
  | Write access or [read-only](#limits) | The task is to change this repo, and a person reviews the pull request. | The task only reads, such as a summary. Either way, give the token only the repos the task needs. |
  | A prompt for each action or a [sandbox](#limits) | There are few actions, and you read each one. | There are many. Let the sandbox and token hold the limits, and prompt only for actions outside them. |
  | AI review or [human review](#check) | You want to find more problems before a person reads the change. | You must decide whether the change is right. |
  | A spec-first tool or a short [criterion](#check) | A large feature where several people must agree on a design. | Most tasks: a few lines and examples are enough. |
  | A survey or a [measurement](#measure) | You want to know what people like and what blocks them. | You want to know whether the work got faster or better. |

  </div>

  ### Current tools <span id="tools"></span>

  Two labels for each tool. **Use** says how widely it is used: Standard, Growing or New. **Maturity** says how settled it is: Stable, Experimental, Draft or Retired. Use labels for agents come from Stack Overflow's 2026 survey: of 12,255 people who answered which coding agents they used in the past year, 65.5% named Claude Code, 58.7% GitHub Copilot, 29.5% Codex and 25.5% Cursor. That counts developers who answered, not teams, and one survey shows no trend. Where no source measures use, the label says so. Versions checked 27 November 2026.

  ### What AI has changed

  - **Agents do the work, not only suggest it.** Cloud agents open pull requests from an issue, and agents run in the terminal as well as in the editor. The leading two in Stack Overflow's survey are used by 65.5% and 58.7% of the developers who answered.
  - **The instruction files became shared standards.** `AGENTS.md`, MCP and Agent Skills are now run by the Agentic AI Foundation, under the Linux Foundation. One file can serve several agents.
  - **Models now approve actions.** Claude Code's auto mode and Copilot's assisted permissions let a model decide which actions need a person. This cuts prompts but does not guarantee safety; sandboxes and deny rules still matter.
  - **Checking the work matters more.** In DORA's 2025 survey, more AI use went with more throughput and with less stable delivery. The survey does not show where the time goes, so measure review time and rework in your own team.
  - **Measuring got harder.** METR could not repeat its 2025 trial cleanly, because many developers would not work without AI.
